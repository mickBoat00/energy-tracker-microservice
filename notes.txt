FINAL VERSION - Authentication with Keycloak & OIDC 

## 1. Adding authentication to my backend

To protect my backend API endpoints, every request must carry a request header with a bearer token that identifies a user and authenticates the request.

In a simple application, I would have an endpoint like /login where the user sends their credentials, I verify they are an existing user, and I generate a JWT token for them which they add to every subsequent request to my backend endpoints.

The reason I don't do that is that authentication is a hard security problem, and I'm entrusting it to a third party: Keycloak. It becomes my Authentication Server. My users interact with Keycloak, and once authenticated, Keycloak gives them an access token - a JWT signed with Keycloak's private key.

## 2. Why a third party (Keycloak)

Pros:
1. Security overloaded to experts - security is a huge part of any application; there's always a new way a system can be hacked. Third-party auth providers like Keycloak have dedicated experts constantly battling vulnerabilities, so the security liability is on them.
2. It saves time - instead of spending hours writing authentication code (which is outside my business logic), I integrate Keycloak to handle identity and access, and spend more time on business logic.

Cons:
- It has a learning curve - I need to understand the concepts behind it (realms, clients, flows), and understanding them takes time.

## 3. Keycloak concepts

Realm - an isolated domain of clients, a set of users, credentials, roles, and groups. A user belongs to and logs into a realm. (Mine is home-energy-tracker.)

Client - the application I want to protect with Keycloak. In my case, the energy tracker application (Postman / future frontend). Clients must be registered with Keycloak.

When creating a client, I pick a client type: OpenID Connect (which I chose) or SAML.

Client authentication switch - defines the type of OIDC client:
- ON -> confidential access (has a client secret)
- OFF -> public access (no secret; browser-based apps)

## 4. OAuth2 - Open Authorization 2

OAuth2 is a protocol where a user grants a third-party application access to their data in a particular service without sharing their password.

Example: a user has contacts saved in Google, and an external application needs access to them. The user can grant access to that app without giving it their Google password.

A simple flow:
- The external app has a "Sign in with Google" button.
- The user clicks it and is redirected to Google to sign in.
- A consent page shows up with the list of permissions the external app is requesting.
- The app made an initial request with a list of scopes, e.g. contacts:get, contacts:delete.
- Once the user agrees, the external app is given an authorization code.
- The app sends the authorization code back to Google in exchange for an access token.
- The external app uses the access token to access those resources.

Key point: OAuth2 is used for granting access to resources (permissions and scopes). It is not designed for authentication - using it alone for authentication is bad.

## 5. OpenID Connect (OIDC)

OIDC is an extension of OAuth2 that adds authentication on top.

- OIDC adds openid to the scope the client requests.
- After the user consents, the client receives an access token, an id token, and access to a /userinfo endpoint.
- The id token is a JWT with information about the user.
- The /userinfo endpoint contains more information about that user.

So: OAuth2 grants access to resources; OIDC grants access to the things needed for authentication (like the user's email) - all without the user sharing their password.

## 6. The complete flow in my application

Actors involved:
- Resource owner - the user (e.g. abena), who owns the credentials.
- Client - my application (Postman / frontend), registered in Keycloak with a client id.
- Authorization server - Keycloak; hosts the login page, issues tokens.
- Resource server - my backend (api-gateway + microservices); only validates tokens.

The flow:
1. My frontend has a "Sign in with Keycloak" button. It redirects the user to the Keycloak auth URL with a request containing scope=openid, my client_id, and a redirect_uri.
2. The user authenticates at Keycloak (login page with username/password).
3. A consent page lists the scopes my app is requesting (in our case openid). The user grants permission.
4. Keycloak redirects the user back to my redirect_uri with an authorization code (a code, not a token).
5. My client sends the code back to Keycloak's token URL, along with client_id and client_secret (confidential client) - this is where the secret is used, never in the browser.
6. Keycloak responds with an access token and id token (JWTs) - and a refresh token for later.
7. My frontend sends the access token JWT to my backend API in the Authorization: Bearer <token> header.
8. My backend verifies the token and grants access - Keycloak only grants access to resources within the scope of the token.

The endpoints/variables that wire this together:
- issuer-uri - Keycloak's identity URL (http://localhost:8091/realms/home-energy-tracker); the JWT's iss claim must equal it; used by the backend to discover the JWKS.
- Auth URL - .../protocol/openid-connect/auth - where the browser is redirected to log in.
- Token URL - .../protocol/openid-connect/token - where the code is exchanged for tokens.
- JWKS/certs URL - .../protocol/openid-connect/certs - the public keys used for verification.
- client_id / client_secret - identify and prove the client.
- redirect_uri - where the code is delivered back to the client.

## 7. My backend as a resource server

My backend becomes the resource server - that's why I have the dependency:

    <dependency>
        <groupId>org.springframework.boot</groupId>
        <artifactId>spring-boot-starter-security-oauth2-resource-server</artifactId>
    </dependency>

I receive requests with headers containing the JWT token. But to understand how I verify it, I first need to understand what that token actually is.

What is a JWT

JWTs are small data packages in JSON format that are cryptographically signed with a private key, containing user details like id, roles, permissions, etc.

The token has the format: <header>.<payload>.<signature>

- The header and payload can be easily decoded (base64) - they're not secret.
- The most important part is the signature - it's how I verify the JWT was actually signed by the issuer (us / Keycloak) and not tampered with.

Verifying the token came from Keycloak

The most important part is to verify the token was from Keycloak using the signature part of the token:

- Keycloak signs JWTs with their private key.
- All I need is their public key to verify the token was signed by my trusted authentication provider.

How do I get the public key?
1. Manually copy the key into my environment - problem: Keycloak rotates its keys frequently, so I'd have to update it constantly; not feasible.
2. The JWKS endpoint (the right way) - Keycloak exposes an endpoint where I can get the public keys used to verify tokens signed by their private keys. My gateway resolves this automatically from the issuer-uri via the discovery document (.well-known/openid-configuration).

Once I get the public key from Keycloak, I verify the signature and decode the header and payload easily with base64 - the user is now authenticated to access resources in my application.

## 8. Client authentication flow options in Keycloak

- Standard flow - standard OIDC redirect-based authentication with authorization code. (OAuth2 spec: Authorization Code Flow.) <- the one I use.
- Direct access grants - the client has access to the user's username/password and exchanges them directly with Keycloak for an access token. (OAuth2: Resource Owner Password Credentials Grant.) This is effectively a /login endpoint.
- Implicit flow - redirect-based authentication without an authorization code. (OAuth2: Implicit Flow - deprecated in OAuth 2.1.)
- Service account roles - the client authenticates itself to Keycloak and retrieves an access token dedicated to this client. (OAuth2: Client Credentials Grant - service-to-service.)
- Standard Token Exchange - enables Standard Token Exchange V2 for this client (exchange one token for another).
- JWT Authorization Grant - JWT Profile for OAuth 2.0 Authorization Grant (an externally-signed JWT acts as the authorization).
- OAuth 2.0 Device Authorization Grant - for apps on devices with limited input capabilities or no suitable browser.
- OIDC CIBA Grant - the user is authenticated via an external authentication device instead of the browser.
- Require PKCE - when ON, the client must prove it's the same app that started the flow (recommended for public clients).
- Require DPoP bound tokens - proof-of-possession: for public clients both access and refresh tokens are bound to a client key; for confidential clients only access tokens (refresh tokens are already sender-constrained).

## 9. Recap - why not just a /login endpoint?

A /login endpoint that returns a JWT is the simplest mental model, but with Keycloak the same effect is achieved through flows: for my browser-based clients I use the standard flow (redirect + code + tokens); if I ever want a plain login-style endpoint for my own clients, I enable direct access grants on a client and keep Keycloak as the identity provider - I never have to build, sign, and rotate JWTs myself.
